# Scoped metric analysis and simpler crash portal

The crash queue leads with open exact incident identities, stored report records, recurrence markers, logs and actions. Access violations retain their presentation family but each real identity and original report remains inspectable. The top incident count counts exact identities, so it can exceed the number of displayed AV family cards. Stored records and reported legacy occurrences remain distinct. Detailed trends/build comparisons/reporting-ID analytics are under the initially collapsed Analysis area; per-card advanced evidence is under More incident data. Search, filters, project build cutoff, tickets and group-resolution/partial-retry behavior are retained.

## Read-only MCP contract (server 0.3.0, 23 tools)

Existing tool names and authentication remain compatible. No caller-supplied SQL, events, player/session IDs, writes or arbitrary query capability is added.

`query_metric` requires `{id: integer, project: "cursemark"}`. Optional string arguments: `created_from` (inclusive), `created_to` (exclusive), `build`, `environment`, `event_type`, `level`. Dates require RFC3339 with timezone and normalize to UTC; string filters match stored values after outer whitespace trimming, maximum 128 bytes, no controls. When both dates are present, from must precede to. Only Cursemark has reviewed gameplay formulas today; other projects and `all` are rejected rather than assigned Cursemark semantics. Use `list_metrics` to discover catalog names. Reviewed gameplay IDs: 88, 117, 130, 131, 104, 107, 132, 102, 121, 122, 123, 124, 125, 126, 127, 128, 83. Raw report cards 38/39 are excluded from this new tool; use existing report reads.

The API `GET /internal/mcp/metric-query/:id` uses existing MCP bearer authentication and strict single-value query parameters. Filters apply to retained, non-soft-deleted source events before aggregation, including nested baselines and event-item joins. They do not filter the output after aggregation. The database schema is resolved internally from the current DB connection, never supplied by a caller. Values are SQL parameters. A leading comment in existing metric 132 is stripped before composing its CTE (also fixes the existing scoped portal query).

Success returns `{columns: string[], rows: any[][], truncated: boolean, updatedAt: RFC3339, metric_id: integer, filters: object, complete: boolean, cohort_note: string}`. Empty results are valid. `complete` means the retained query result was not cut by the 1,000-row result bound; it is not a claim of complete lifetime telemetry. The cohort note identifies partial-session/window semantics and PID caveats. The same filters, including baselines, form the cache key. Up to two calculations run concurrently, 45-second query budget, five-minute cache, at most 128 cached metric/filter combinations shared with existing metrics. Serialized new responses above 1 MiB fail wholly (413, complete false). Errors are never represented as empty successes. Unknown/repeated filters fail validation. Existing metric formulas, formula labels and retained-event coverage are not statistical exposure denominators. Date, event-type or level filters may truncate runs/sessions, so AI must interpret those cohort limitations.

`get_crash_health` requires `{project: string}` (exact project ID, or explicit `all`); optional `days` is 7, 30 or 90, default 30. `GET /internal/mcp/crash-health?project=...&days=...` retains the current detailed-receipt/build/daily/returned-incident aggregate fields, but returns null groups/families rather than closed issue metadata or raw stacks/PIDs. It is not a group-membership index. The underlying health model remains bounded at 100,000 records; incomplete health fails with complete false. New output is capped at 1 MiB. Existing `list_active_crashes`/`get_crash` supply issue details and membership when needed.

The original `list_metrics`/`get_metric` contracts are retained; `get_metric` uses its existing default-project behavior and cannot take these new filters. Prefer `query_metric` for explicitly scoped gameplay analysis. The new tools are read-only and idempotent; metric labels and source report text remain untrusted data.

No schema migration, client/breadcrumb change, source rebaselining, automatic resolution, ticket movement or community reactions are required. Existing independent per-project crash acceptance cutoffs and 05:00 America/Los_Angeles collectors are unchanged. The separate 05:30 AI automation remains managed by the parent task.
