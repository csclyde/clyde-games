# Crash health read model

`GET /crash/health?project=<exact project ID or all>&days=7|30|90` uses the existing admin authentication and cross-origin protections. It changes no data and adds no schema. A missing project defaults to `all`; an empty/oversized project or invalid day window returns 400. The query reads only non-deleted records, selecting metadata and no raw stacks. It is bounded at 100,000 records across retained history; an exceeded cap returns 413 with `complete:false`, without a misleading partial aggregate. Time windows are rolling receipt windows with UTC calendar-day buckets; first/last buckets may be partial.

## Measures

- `reports`: one stored `OccurrenceVersion=1` record with non-zero `IngestedAt` in `[from,to]`. The detailed row's Count does not weight this measure. Transport retries are separate stored reports because the client supplies no occurrence idempotency token.
- `reporting_ids`: distinct trimmed non-empty client PIDs among those records, qualified by project. Repeated IDs across builds or issue groups count once in the overall/family impact total. These are a reporting-installation proxy only: the schema does not establish verified people, active installations or sessions. Missing-ID reports are counted separately.
- `daily`: stored detailed receipts and distinct reporting IDs by UTC date. Dates before the first retained detailed receipt are marked as unavailable detailed history in the UI, not represented as proof of zero crashes.
- `builds`: per-project submitted build identifiers, recent detailed report counts, reporting IDs, exact group count, current open report count, returned report count and first/last detailed receipt in the window. Legacy aggregate Count is never attributed to its representative build. These are reporting-volume comparisons; no crash rate, crash-free percentage or stability improvement is inferred without an exposure denominator.
- `first_received` / `last_received`: earliest/latest known server receipt among retained detailed records, across all stored history for the selected scope. They are not client failure timestamps or a reconstructed historical first occurrence. Missing, zero or future receipt times are excluded from timed statistics; untimed/out-of-range detailed records are counted separately. Displayed timestamps use the browser locale; chart buckets use UTC.
- `legacy_rows` / `legacy_occurrences`: retained non-deleted rows whose occurrence format is not version 1, and the sum of their original reported Count. Legacy records never supply timeline events or reporting-ID counts. Project attribution follows retained row metadata; older cross-project aggregation and overwritten build/PID/time metadata cannot be reconstructed. The deployment audit verifies the actual retained legacy counts are non-null.
- `open_groups`: current exact identities with an explicitly open retained record. Unknown null resolution flags follow the existing queue's exclusion semantics. A missing group identity remains a separate report, not a guessed match. The AV family is presentation-only, so this count can exceed the number of displayed issue rows.
- `returned_open_groups`: groups with a known latest `ResolvedAt` and a currently open detailed receipt strictly later than it. `returned_reports` / `returned_reporting_ids` measure that open returned impact within the selected receipt window. This identifies return after a recorded resolution, not proof of a code regression or a complete historical reopen count. Legacy CreatedAt/UpdatedAt and resolved flags without resolution timestamps never establish a return.

The response includes `project`, `days`, `from`, `to`, `complete`, `stored_rows`, global measures, `daily`, `builds`, exact `groups` and per-project AV `families`. Family reporting IDs and returned impact are deduplicated directly, not summed from member-group counts. PIDs and raw stacks are not returned by this aggregate endpoint. Resolved reports remain in receipt/build history; the open queue still uses the existing complete active reports and retains each individual raw record and true identity.

## Admin behavior

The crash page has health counters, receipt activity with unavailable-history shading, build comparisons, historical coverage, and an open issue queue with search, receipt/report/impact sorting and returned/detailed/legacy filters. Selecting a build filters matching open issue rows without truncating a group's members. Resolution still acts on each represented complete original group across builds. AV presentation-family collapse, individual report inspection, ticket creation without resolution, partial resolution retry, project isolation and per-project oldest accepted build controls are preserved. Health reloads after resolution. Failed/stale project requests cannot show another project's aggregate or fake zero values.

No client changes, breadcrumbs, occurrence regrouping, administrative resolution, synthetic production crashes, community messages, or source syncs are triggered by the health UI or read model. The collector's persisted source configuration, fixed no-backfill floors and separate AI workflow are independent.

## Verification and deployment

Semantic tests cover legacy weighting, duplicate/missing IDs, cross-project qualification, receipt boundaries, absent/future receipt times, exact group returns, AV-family impact deduplication, no invented return from unknown history, raw-row immutability and API window/auth contracts. Disposable MySQL tests verify actual `p_id` column mapping, project filtering, soft deletion, null resolution handling and read-only field preservation. Native API/MCP full/race/vet, the bot suite and production admin build are run for release.

`scripts/crash-health-smoke.cjs` covers health labels, legacy exclusion, build/search/returned filters, AV details, partial retry, project-response races, failure states and responsive layouts. `scripts/crash-smoke.cjs` retains detailed metadata, ticket retention, bulk/project-scoped resolution and retry coverage; `scripts/admin-cleanup-smoke.cjs` checks prior Panel/AV cleanup. Set `PLAYWRIGHT_MODULE`, `ADMIN_PUBLIC_ROOT` and optional `UI_EVIDENCE_DIR` for an isolated built-admin preview. Every API request is mocked and external requests are blocked.

`scripts/deploy-crash-health.py` stages an API/admin-only cutover with a fresh private backup, repeated read rehearsal against a restored copy, field fingerprints and configuration snapshots. There is no schema migration. It installs immutable admin assets while retaining the existing index's other content and live shared stylesheet. API rollback restores the preceding baseline/configuration-aware binary and previous admin index; no database restore or data deletion is required. Newly received reports remain intact. MCP, Little Clyde, source configuration, cutoffs, authentication and public-site assets are verified unchanged.
